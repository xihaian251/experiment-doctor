## 1. 实现内容

### 1.1 Lock Schema（`v1/lock/schema.py`）

- `ExperimentLock`：8 个块（identity / code / dataset / configuration /
  randomness / environment / execution / artifacts）+ `schema_version="1.0"` +
  `lock_hash`。**每一个 leaf 都是 v0.1 的 `ProvenanceField`**（value + status +
  source + note），零新增证据原语、零修改 v0.1 schema。
- UNKNOWN 纪律由 v0.1 已有的 pydantic 校验器强制：`UNKNOWN` 不得携带 value，
  `CONFIRMED`/`SUPPORTED` 必须引用 source。因此**一张 lock 在构造层面就无法
  存进一条伪造事实**——这是本轮最重要的结构性保证。
- 所有块的默认值都是 `_unknown(name)`（带"not captured at init time"备注），
  `build_lock` 只覆盖真实捕获到的字段。
- canonical serialization：`json.dumps(body, sort_keys=True,
  separators=(",",":"), ensure_ascii=False)`；`lock_hash =
  "sha256:"+sha256(canonical_json)`；`seal()` 返回带 hash 的副本，`body()` 排除
  `lock_hash` 自身。篡改任意字段 → hash 失配（有专门测试）。
- `execution.start_time` 在 Phase 1 恒为 `UNKNOWN`：init 时 run 尚未开始，由
  Phase 2 的 `run` wrapper 观测填入。任务书 Step 1 简化 schema 无 budget 块
  （计划 §4 的 `execution.budget` 留待 Phase 2），如实登记见 §5.1。

### 1.2 Capture Layer（`v1/capture/`，subprocess + stdlib，无 GitPython）

- **`git.py`**：`repository_root`（`rev-parse --show-toplevel`）、
  `repository_url`（`remote get-url origin`，无 origin 时回退为根路径并以
  `SUPPORTED` 分级而非冒充 CONFIRMED）、`current_commit`（`rev-parse HEAD`）、
  `is_dirty`（`status --porcelain`，**含未跟踪文件**——未跟踪脚本同样会改变运行
  结果）、`diff_hash`（`sha256(git diff 输出 + 排序后的未跟踪文件名与内容)`；
  clean 树返回 `UNKNOWN` 并注明"no diff to hash"——把"没有可哈希的东西"如实
  记录而不是伪造一个空哈希）。git 缺失/非仓库/调用失败一律 `UNKNOWN` 无值。
- **`environment.py`**：`python_version`（`sys.version` 解析）、
  `installed_packages`（`importlib.metadata` 全量 name→version 排序字典）、
  `platform_info`。三者均为对当前解释器的**直接观测**，`CONFIRMED`。
- **`runtime.py`**：`now_iso/timestamp_field`（UTC ISO-8601）、
  `working_directory`、`declared_command(command)`——未传 `--command` 时返回
  `UNKNOWN` 并注明"the invoked command is not inferred"（init 是独立进程，
  父 shell 的调用命令行不可靠可观测，宁 UNKNOWN 不猜）。

### 1.3 Lock 构建与写入（`v1/lock/writer.py`）

- 值进入 lock 只有两扇门：**直接观测**（git/environment）或**显式声明**
  （`--seed/--command/--config/--dataset/--output-dir`），永不经过推断。
  `seed_source` 字段记录声明通道（"cli --seed"），使证据来源本身也被审计。
- `hash_file`（64KB 分块 sha256）、`hash_tree`（排序 relpath+内容哈希清单再
  sha256，顺序无关）；`_fingerprint_paths` 对声明但缺失的路径记入
  `confidence_note`（"declared but not found"），全部缺失则字段整体 `UNKNOWN`
  ——不伪造指纹。声明在项目根之外的路径用原始路径作 key（`_rel_key` 防
  `relative_to` 越界）。
- 非 git 目录：`CodeBlock()` 全 `UNKNOWN` 带解释备注，其余块照常捕获。

### 1.4 CLI（`v1/cli.py` + `cli.py` 末尾一行加法注册）

`experiment-doctor init [PATH]` 在（默认当前）目录生成
`experiment.lock.json`，回显 lock 路径、`lock_hash` 与逐字段证据分级清单。
选项：`--command --seed --config(可多次) --dataset(可多次) --output-dir -o`。
对 v0.1 的唯一改动是 `cli.py` 末尾 `app.command(name="init")(v1_init)` 加上一
行 import 和更新后的 docstring——v0.1 四命令（scan/audit/rules/adapters）实现
逐字未动，有专门测试断言其 `--help` 仍正常。

## 4. 测试结果

- **新增测试：21 个**（要求 ≥10），`tests/test_v1_lock_capture.py`，全部在临时
  目录 copytree fixture + `git init/commit` 后运行（不依赖网络/真实项目）：
  - T1 commit 可恢复：clean 仓库 lock 中 commit == `git rev-parse HEAD`；
  - T2 dirty 检测：tracked 修改与 untracked 新增分别翻转 `dirty=True` 并改变
    `diff_hash`；clean 树 `diff_hash` 为 UNKNOWN 而非假哈希；
  - T3 python version：lock 值 == 当前解释器版本，CONFIRMED 带 source；
  - T4 command 捕获：`--command` 声明 → CONFIRMED；未声明 → UNKNOWN 且
    confidence_note 说明不推断；
  - T5 未知字段保持 UNKNOWN：未声明 seed/dataset/config/output 的 lock 里对应
    字段 value=None + status=UNKNOWN；**`test_T5_seed_is_not_read_out_of_config`**
    断言 fixture config 里的 `seed: 3` 不会泄漏进 lock；
  - 其余：packages/platform 观测、声明 seed CONFIRMED、非 git 目录 code 块全
    UNKNOWN、文件/目录指纹确定性、声明缺失路径不伪造、canonical_json 幂等 +
    同环境重复生成 hash 一致、篡改 seed 后 hash 失配、UNKNOWN 序列化无 value、
    `ExperimentLock.model_validate_json` round-trip、CLI init 端到端
    （Typer runner）、v0.1 四命令 `--help` 退出码 0。

  本轮 21。
- `ruff check src tests scripts` → All checks passed；`ruff format --check .` →

## 5. 与 v0.1 UNKNOWN 问题的对应关系（本轮核心验收）

对照三项目取证报告中的具体缺口，逐项回答"哪些已经被 lock 捕获"：

### 5.1 GMMVI（归档取证：seed 0/3,483、commit 0/7,004、sed 注入预算）

| v0.1 缺口 | Phase 1 后 |
|---|---|
| **seed 无处可查**（0/3,483 文件记录 seed，只能从副本数反推"可能有种子"） | **已捕获**：`--seed 42` → `randomness.seed=42 CONFIRMED` + `seed_source="cli --seed"`。同时**证明不越界**：config 里写着 seed 也不读（T5 测试），因为"配置里有个种子"≠"这次运行用了它"——这正是 v0.1 判定 INFERRED 上限的场景。 |
| **commit 无从恢复**（0/7,004 文件记录产生码的 commit；`implemented_*` 语义被迫 CONFLICTING，即 CRDA-OBS-1 同源问题） | **已捕获**：`code.commit CONFIRMED`（观测 HEAD），`dirty + diff_hash` 把"HEAD 之外的本地修改"也纳入可审计范围。归档场景下 GMMVI-OBS-1（implemented_* 假设检出轨=产生码）从根源上消失：lock 记录的就是产生码那一瞬间的树状态。 |
| **budget UNKNOWN**（`sed -i` 注入脚本的运行时预算，静态读码不可恢复） | **未捕获，如实登记**：任务书 Step 1 简化 schema 无 budget 块（计划 §4 的 `execution.budget` 属 Phase 2 `run` wrapper 职责——预算只有在进程被包裹时才存在可观测对象）。Phase 1 不预设为其留字段，避免造出永远 UNKNOWN 的空壳。 |

### 5.2 TorchSSL（验收：environment UNKNOWN + code mismatch）

| v0.1 缺口 | Phase 1 后 |
|---|---|
| **运行环境整体 UNKNOWN**（归档无环境记录，包版本/解释器不可恢复） | **已捕获**：`environment.{python_version, packages(全量 name→version), platform}` 三字段直接观测 CONFIRMED。注意这是 v1 相对 v0.1 的本质优势：环境在 init/run 时刻**只被读取一次即永久固化**，不依赖用户事后还留着那个 venv。 |
| **code mismatch**（检出轨检出码 ≠ 归档日志的产生码，best−last 差距超过 spread 的疑点无法归因） | **机制上可检出**：commit+dirty+diff_hash 唯一确定产生码的树状态；两次运行 lock 一比，码不同即暴露。T1/T2 测试即该机制的最小验证（改一行 → dirty/diff_hash 变）。 |

### 5.3 CRDA（验收 2：runtime environment None×1350）

| v0.1 缺口 | Phase 1 后 |
|---|---|
| **runtime environment 字段 1,350 条全为 None**（元数据里声明过环境但运行时从未记录，声明≠运行时无法对账） | **已捕获且分离**：lock 的 `environment` 块是对**实际执行 lock 的解释器**的一手观测（`sys.version`/`importlib.metadata`），与任何"声明的 env 文件"天然分层——Phase 2 verify 即可做 declared-vs-observed 对账，ED 系列规则的 spread/矛盾类检查在有新证据可查。 |
| 已声明但从未运行的配置（CRDA-OBS-1 implemented_* 语义） | 同 5.1：lock 只描述"这一次"，声明与实际运行的分离由逐 run 一份 lock 的结构保证。 |

### 5.4 汇总

- **已被 lock 捕获**：GMMVI commit、GMMVI seed（声明通道 + 不推断证明）、
  TorchSSL environment、TorchSSL code mismatch 检出机制、CRDA runtime
  environment。
- **结构性转化**：这些字段从 v0.1 的"永久 UNKNOWN / CONFLICTING（归档不可恢
  复）"变为 v1 的"运行前/运行时一次捕获即 CONFIRMED"。核心假设——**主动捕获
  可把不可恢复的 UNKNOWN 转化为可验证证据**——在 Phase 1 范围内成立。
- **仍未覆盖（诚实清单）**：GMMVI budget（Phase 2）、`execution.start_time`
  （Phase 2）、Hydra/MLflow/W&B 等第三方 tracker 的既有记录（v1.1 裁决）、
  audit 侧对 lock 的消费（禁止项，未动）。
